## Executive Summary

LaborLedger is a TypeScript/pnpm monorepo for a multi-company labor operations platform with:

- NestJS API on port 4000.
- Next.js Admin app on port 3000.
- Next.js Field PWA on port 3001.
- PostgreSQL/Prisma database package.
- PM2 + Nginx VPS deployment model.

The repository has a meaningful domain model, clear package boundaries at the workspace level, many automated test files, strict TypeScript settings, and deployment documentation. However, audit confidence is materially reduced by a very dirty working tree, absent CI workflows, failed local test/typecheck commands due missing local toolchain links, heavy BFF route duplication, and security-sensitive Field session design issues.

## 1. Stack and Architecture Inventory

**Score: 3 / 5 — Adequate baseline, notable gaps remain**

### Evidence

- Root workspace uses pnpm: `package.json` has `"packageManager": "pnpm@11.5.2"`.
- Workspace packages are declared in `pnpm-workspace.yaml`: `apps/*`, `packages/*`, and `tests`.
- README identifies:
  - API: NestJS, `apps/api`, port 4000.
  - Admin: Next.js, `apps/admin`, port 3000.
  - Field PWA: Next.js, `apps/field`, port 3001.
  - Database: PostgreSQL + Prisma, `packages/database`.
- `apps/api/src/main.ts` bootstraps NestJS `AppModule`, applies security/rate-limit middleware, and listens on `process.env.PORT ?? 4000`.
- `apps/api/src/modules/app.module.ts` wires a large domain module set including identity, company operations, kiosk, worker, field, mobile, invoices, VIN decode, storage, vehicle photos, and mechanic orders.
- Prisma schema uses PostgreSQL via `env("DATABASE_URL")` and includes multi-tenant entities such as `Group`, `Company`, memberships, sessions, audit events, mobile devices, field sites, work orders, shifts, and invoices.
- Deployment uses PM2 via `ecosystem.config.cjs` with API/Admin/Field processes.

### Findings

- **Clear monorepo boundaries:** app/package separation is understandable.
- **Domain-rich backend:** API modules map to business capabilities and multi-company tenancy.
- **Large central Nest module:** `AppModule` imports/controllers/providers list is large and manually wired, which may increase coupling and change risk.
- **BFF integration pattern:** Admin and Field Next.js route handlers proxy to the Nest API using `API_BASE_URL`, cookies, kiosk credentials, or field-service credentials.
- **External integrations:** PostgreSQL/Prisma, NHTSA VPIC VIN decoding, Resend email, PDF generation, QR codes, file upload/storage, ZXing WASM scanning, PM2/Nginx deployment.

### Gaps / Residual Risks

- No architecture decision records or system boundary diagram were found in active top-level docs.
- App boundaries are present but many cross-app proxy routes appear hand-written rather than generated or shared.
- Current working tree deletes many local guidance/docs files and adds new mobile-device work, so this audit reflects a volatile state.

## 3. Security Posture

**Score: 2 / 5 — Emerging baseline with security-sensitive gaps**

### Security Findings Table

| ID | Severity | Finding | Evidence | Recommendation |
|---|---|---|---|---|
| SEC-01 | high | Field session cookie stores employee PIN inside signed-but-not-encrypted payload. | `apps/field/src/lib/field-session.ts` defines `FieldSessionData` with `pin`, base64url JSON encoding, HMAC signature, and `toPublicFieldSession` omits PIN only after decoding. | Do not store PINs in client-held session payloads. Store opaque session IDs server-side or remove PIN from session entirely. |
| SEC-02 | high | Field session signing secret can fall back to `KIOSK_SECRET` or `WORKER_COMPANY_ID`, with `WORKER_COMPANY_ID` likely non-secret. | `getSessionSecret()` in `apps/field/src/lib/field-session.ts` uses `FIELD_SESSION_SECRET ?? KIOSK_SECRET ?? WORKER_COMPANY_ID`. | Require a dedicated high-entropy `FIELD_SESSION_SECRET`; fail closed if absent. |
| SEC-03 | medium | In-memory rate limiting is per-process and trusts forwarded IP headers without explicit proxy trust model. | `apps/api/src/main.ts` and `apps/field/src/middleware.ts` use module-level `Map` buckets and `x-forwarded-for`/`x-real-ip`. | Move security-sensitive rate limits to a shared backing store or edge proxy; document trusted proxy assumptions. |
| SEC-04 | medium | No dependency vulnerability audit was run and no CI dependency scanning was found. | No `.github/workflows/*`; audit avoided network/cache-generating commands. | Add non-mutating CI dependency audit/scanning with pinned policy and scheduled runs. |
| SEC-05 | medium | File storage path resolution lacks explicit containment normalization check. | `apps/api/src/modules/storage/storage.service.ts` joins `storageRoot` and `filePath` in `resolveAbsolutePath()`. | Normalize and verify resolved paths remain under `storageRoot`; validate DB-stored paths before filesystem access. |
| SEC-06 | low | Production deployment script reads `.env.production` and installs/builds on server; operational safeguards exist but secrets lifecycle is manual. | `deploy/README.md`, `deploy/deploy-vps.sh`, `ecosystem.config.cjs`. | Add secret rotation/runbook guidance and avoid manual env drift. |
| SEC-07 | informational | Good cookie and password primitives are present. | API session cookie uses `HttpOnly; Secure; SameSite=Lax`; password hashing uses argon2id. | Preserve these patterns and add tests around cookie flags and password reset/session expiry. |

### Positive Security Evidence

- API session cookies are serialized with `HttpOnly`, `Secure`, `SameSite=Lax`, and `Max-Age`.
- Password hashing uses Argon2id with configured memory/time/parallelism.
- Kiosk credentials are verified with Argon2 hashes.
- Mobile auth uses bearer guard and a required pepper of at least 32 characters.
- API and Field set basic security headers.
- Authenticated, superadmin, kiosk, field-service, and mobile-bearer guards exist and are applied to many controller routes.
- Prisma schema includes token hashes, expiration fields, revocation fields, audit events, and tenant scoping fields.

### Residual Risks

- This audit did not read secret files, so actual production secret quality/configuration is unknown.
- The volatile worktree includes mobile auth changes not independently verified.
- Because local tests/typecheck failed before execution, security regressions may exist undetected.

## 5. Technical Debt and Dead/Duplicated Code

- Example duplication: `apps/admin/src/lib/api-bff.ts` provides `requireSessionCookie()`, but `apps/admin/src/app/api/company-operations/employees/[employeeId]/route.ts` uses both the helper and an inline cookie check in the same file.

- Grep found stub/default VIN decoder references; `VIN_DECODER` defaults to `"stub"` in `apps/api/src/modules/vin-decode/vin-decode.service.ts`.

### Findings

- **High churn / dirty tree:** Auditability is reduced because many files are modified, deleted, or untracked.
- **BFF boilerplate duplication:** Admin and Field route handlers repeat fetch/proxy/session logic across many files.
- **Central module coupling:** The API has a large composition root rather than smaller feature modules.
- **Stub defaults:** VIN decoder defaults to stub mode unless configured; useful for development but risky if production env is incomplete.
- **Tooling inconsistency:** Local dependency state does not satisfy test/typecheck commands.

### Residual Risks

- Dead-code assessment is incomplete because the working tree includes mass deletions and untracked additions.
- No static unused-code analyzer was run.
